# Дизайн: фильтрованные связи свитч-свитч

Дата: 2026-08-28
Статус: утверждён (расширение варианта A из `2026-08-23-filtered-links-design.md`)

## Проблема

Фильтрованные связи (`Link.Filter`, `docs/superpowers/specs/2026-08-23-filtered-links-design.md`)
сегодня разрешены только между двумя роутерами. Связь свитч-свитч всегда
безусловно сливает оба свитча в один плоский L2-домен (`assignL2Domains` в
`internal/graph/graph.go`) — все устройства, подключённые к любому из двух
свитчей, становятся взаимно достижимы за один хоп через синтетический
bus-узел домена.

На практике реальный транк между двумя свитчами не обязан анонсировать все
сети по обе стороны: `core-chap` и `core-zhuk` физически связаны одним
транком, но не каждая подсеть за одним свитчем должна быть видна маршрутам
через другой. Диагностика (`internal/diagnose`) и компилятор правил
(`internal/compiler`) в текущей модели не могут этого выразить: единственный
способ — вообще разорвать линк, потеряв реальную связность.

Нужно то же route-filtering (aExports/bExports), что и для роутер-роутер
линков, но применённое к связи двух свитчей.

## Решение

Фильтрованный switch-switch линк **не участвует** в слиянии L2-доменов.
Свитчи по обе стороны такого линка остаются каждый в своём домене (как
сегодня «одинокий» свитч без switch-switch связей). Сам линк превращается в
анонс-ориентированное ребро между двумя доменными bus-узлами — структурно
идентично тому, как уже работает фильтрованный линк роутер-роутер, только
на концах ребра доменные узлы (`NodeDomain`) вместо `NodeRouter`.

Смешанный router-switch фильтрованный линк по-прежнему запрещён: для него
нет естественной пары «двух доменов», которые можно было бы разделить.

## Валидация

`internal/topology/validate.go`, текущая проверка (~строка 71):

```go
if t.Devices[l.A.Device].Kind != DeviceRouter || t.Devices[l.B.Device].Kind != DeviceRouter {
    return fmt.Errorf("%s: filtered link must connect two routers", where)
}
```

меняется на «оба конца одного рода, и это либо оба роутера, либо оба
свитча»:

```go
aKind, bKind := t.Devices[l.A.Device].Kind, t.Devices[l.B.Device].Kind
if aKind != bKind || (aKind != DeviceRouter && aKind != DeviceSwitch) {
    return fmt.Errorf("%s: filtered link must connect two routers or two switches", where)
}
```

Остальные проверки (`AExports`/`BExports` резолвятся в известные сущности,
оба списка обязательны) не меняются — `exportSubnets` уже kind-агностична.

## Граф (`internal/graph/graph.go`)

### Разделение switch-линков

Сегодня `Build` собирает все switch-switch линки в `switchLinks` и передаёт
их в `assignL2Domains` целиком. Меняем: в группировку доменов идут только
**нефильтрованные** switch-switch линки. Фильтрованные откладываются в
отдельный список `filteredSwitchLinks` и обрабатываются после того, как
`domainOf` посчитан.

### Ребро между доменами

Для каждого линка из `filteredSwitchLinks`:

```go
domA, domB := domainOf[l.A.Device], domainOf[l.B.Device]
if domA == domB {
    continue // уже слиты другим, нефильтрованным путём — фильтровать нечего
}
aExports, err := exportSubnets(topo, l.Filter.AExports)
bExports, err := exportSubnets(topo, l.Filter.BExports)
g.addEdgeAllow(domainNode(domA), domainNode(domB), &edgeAllow{To: bExports})
g.addEdgeAllow(domainNode(domB), domainNode(domA), &edgeAllow{To: aExports})
```

Ветка `domA == domB` — осознанное поведение (как и у роутеров: избыточный
нефильтрованный путь делает фильтр на другом линке бессмысленным), не
ошибка.

### Создание bus-узла при малом числе точек

Сегодня: `if len(points) < 2 { continue }` — домен с одной точкой
присоединения (или без них) не получает bus-узла, потому что «нечего с
ней соединять». Это больше не всегда верно: домен с одной локальной точкой
может быть концом фильтрованного switch-линка — тогда его единственная
точка обязана дотянуться до bus, иначе окажется отрезана от остального
графа.

Перед циклом создания bus-узлов собираем `domainsWithFilteredLink :=
map[string]bool` из `domA`/`domB` каждого обработанного
`filteredSwitchLinks`, и меняем условие на:

```go
if len(points) < 2 && !domainsWithFilteredLink[name] {
    continue
}
```

### Слияние повторных рёбер (`addEdgeAllow`)

Сегодня повторный вызов с тем же `(from, to)` молча игнорируется — это
было безопасно, пока единственный источник дублей — сам код (idempotent
guard), а не реальные данные. С доменными рёбрами два разных
switch-switch линка (разные пары физических свитчей) могут разрешиться в
одну и ту же пару доменов. Молчаливый пропуск второго уничтожит его
экспорт. Меняем на слияние:

- если существующее ребро `Allow == nil` (безусловное) — ничего не
  делаем, оно уже не ограничивает сильнее любого нового;
- если новое `allow == nil` — заменяем существующее ограничение на
  безусловное (реальная маршрутизация: если хоть один анонс
  безусловный, соединение безусловно);
- если оба `Allow != nil` — объединяем множества `Allow.To` (union), не
  создавая второй записи в `adj`.

## Reachability для UI-кандидатов (`internal/graph/reachable.go`)

`ReachableEntities` сегодня всегда стартует с `RouterNode(device)`. Такого
узла для свитча в графе никогда не было (свитчи существуют только как
доменные bus-узлы) — `plainReachableSubnets` от несуществующего узла не
находит ничего, и кандидаты для стороны-свитча уже сегодня молча пустые.
Это была немая, но безобидная деградация, пока switch-switch фильтр был
запрещён валидацией; теперь её нужно исправить.

**Исправлено по факту реализации (см. план, Task 4):** вариант выше —
единственный доменный узел как стартовая точка — оказался сломан. `Build`
подключает локальные точки домена к его bus-узлу только когда их ≥2 или
домен держит **выживший** фильтрованный линк — а `ReachableEntities` всегда
исключает именно тот линк, о котором спрашивает вызывающий, что рутинно
оказывается единственным основанием для существования bus-узла. Поэтому
доменный узел в обрезанном графе регулярно остаётся без рёбер, и наивная
версия выше проваливает свой же тест уже на первом сценарии.

Рабочее решение — `startNodes` (во множественном числе): свитч
разрешается не в один доменный узел, а в набор из самого доменного узла
**плюс** каждую его точку присоединения напрямую (каждый роутер на этом
домене, каждая подсеть, чья сеть подключена к свитчу этого домена).
`plainReachableSubnets` соответственно принимает `[]Node`, а не один `Node`,
и стартует BFS от всех переданных узлов сразу:

```go
func startNodes(topo *topology.Topology, device string) ([]Node, error) {
    d, ok := topo.Devices[device]
    if !ok {
        return nil, fmt.Errorf("unknown device %q", device)
    }
    if d.Kind == topology.DeviceRouter {
        return []Node{RouterNode(device)}, nil
    }
    plainLinks, _ := splitSwitchLinks(topo)
    domainOf := assignL2Domains(topo, plainLinks)
    domain := domainOf[device]
    seen := map[Node]bool{}
    var starts []Node
    add := func(n Node) {
        if !seen[n] {
            seen[n] = true
            starts = append(starts, n)
        }
    }
    add(domainNode(domain))
    // + каждый роутер, присоединённый к этому домену через switch-router
    //   линк, + каждая подсеть сети, присоединённой напрямую к свитчу
    //   этого домена — см. internal/graph/reachable.go для полного кода.
    return starts, nil
}
```

Доменный узел всё равно нужен как один из seed'ов: он остаётся значимым,
когда домен участвует ещё в одном, не исключённом сейчас фильтрованном
линке — тогда через bus доступно то, что re-derive по локальным точкам
топологии не восстановит.

`ReachableEntities` считает `domainOf` на урезанном (`trimmed`) графе тем
же путём, что и `Build` (теми же извлечёнными помощниками `splitSwitchLinks`/
`assignL2Domains`), и стартует `plainReachableSubnets` с `startNodes(...)`
вместо `RouterNode(device)` напрямую.

Известный технический долг: `startNodes` независимо повторяет перечисление
точек присоединения домена (switch-router линки + сети, подключённые к
свитчу), которое `Build` уже делает при сборке `domainPoints`. Сегодня оба
места согласованы, но это не вынесено в один общий помощник, как
изначально предполагалось выше, — расхождение придётся ловить руками, если
`Build`-версия обзаведётся новым видом точки присоединения. Оставлено как
дальнейшее рефакторинговое улучшение, не блокирующее эту фичу.

`ValidateFilterExports` не меняется — она уже вызывает `ReachableEntities`
по обеим сторонам любого фильтрованного линка независимо от рода
устройства.

## HTTP API и UI

Без изменений контракта. `links.js`/`links.html`/канвас (`topology.js`)
уже родовые по `link.filter` и не проверяют `Device.Kind` — они начнут
корректно работать для switch-switch линков сразу после исправлений в
`graph`/`reachable`. Единственная причина, по которой это не работало
раньше, — сама валидация топологии и пустые кандидаты из
`ReachableEntities`.

## Поведение отрезанных пар

Не меняется относительно `2026-08-23-filtered-links-design.md`: если после
учёта всех фильтров (включая switch-switch) для пары src/dst не осталось
ни одного пути — правило никуда не ставится, трафик диагностируется как
заблокированный default policy. Асимметрия между направлениями (путь есть
в одну сторону и отсутствует в другую) остаётся нормальным поведением,
`diagnose.Report.ReturnPathAllowed`/`ReturnRouteExists` показывают её
так же, как и для роутер-роутер фильтров.

## Тестирование

| Слой | Что покрываем |
|------|---------------|
| topology/validate | фильтр разрешён свитч-свитч; запрещён смешанный router-switch; остальные правила валидации не регрессируют |
| graph | домены разделяются фильтрованным switch-линком; путь проходит только при подходящих экспортах и отсечён при неподходящих; домен с одной точкой присоединения создаётся, когда участвует в фильтрованном линке, и не создаётся иначе; `domA == domB` не создаёт ребро; два switch-линка на одну пару доменов объединяют экспорты (union), а не теряют один из них |
| graph/reachable | кандидаты `ReachableEntities` для стороны-свитча совпадают с реально достижимыми подсетями через домен |
| diagnose | воспроизведение исходного бага пользователя: `it-users → omsk16` остаётся единственным путём при текущих (нефильтрованных) связях; после перевода `core-chap|core-zhuk` в фильтрованную связь с подходящими экспортами появляется путь через `omsk13`/`omsk14` → `omsk2`/`omsk3`, если топология это действительно допускает |
| web (node --test) | `links_page`, `topology_render` — прогнать существующие наборы, регрессий не ожидается, явных новых сценариев не требуется (UI уже родовой) |
