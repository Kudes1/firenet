# Дизайн: фильтрованные связи в топологии

Дата: 2026-08-23
Статус: утверждён (вариант A — фильтр как атрибут связи)

## Проблема

Связь (`Link`) сегодня означает полную связность: любые подсети могут
проходить через неё. Компилятор ставит правила на все роутеры вдоль всех
простых путей между парами подсетей, поэтому при избыточной топологии
трафик идёт и в обход задуманных маршрутов (например, Магазин → Главный
офис через Дата-Центр).

Нужен способ ограничить, какие сети «анонсируются» через конкретную
связь — семантика route-filtering (как prefix-list в BGP), применённая
к размещению firewall-правил.

## Решение

Фильтрованная связь — та же сущность `Link` с опциональным полем
`Filter`. Семантика: **списки экспорта по сторонам**. У каждого конца
связи список экспортируемых сущностей (сетей или отдельных подсетей).
Пакет от src-подсети S к dst-подсети D может пересечь фильтрованную
связь в направлении A→B тогда и только тогда, когда

    S ∈ resolve(AExports)  &&  D ∈ resolve(BExports),

где `resolve` разворачивает имя сети в её подсети, а имя подсети — в саму
подсеть. Это естественно выражает асимметрию («магазин отдаёт только
MARKET, получает только MAIN») и транзитные запреты (Главный офис не
доступен Магазину через Дата-Центр, если связь market–DC экспортирует
только MARKET↔MAIN).

## Модель данных

`internal/topology/model.go`:

```go
// LinkFilter restricts which networks/subnets each side exports
// across the link (route-filter semantics).
type LinkFilter struct {
    AExports []string // entities side A announces across the link
    BExports []string // entities side B announces across the link
}

type Link struct {
    A, B   Endpoint
    Filter *LinkFilter // nil = обычная связь полной связности
}
```

- Экспорт — имена сущностей: network или subnet (смешанный уровень).
  Дубликаты схлопываются, порядок не значим.
- `Filter == nil` — обычная связь; обратная совместимость с текущим YAML.

### YAML

```yaml
links:
  - a: {device: market}
    b: {device: test1}
    filter:
      a-exports: [MARKET]
      b-exports: [MAIN, mr-1]
```

Поле опционально (`KnownFields(true)` сохраняется): существующие файлы
читаются без изменений.

## Валидация

`internal/topology/validate.go`, новые проверки:

1. Связь с фильтром соединяет только роутер–роутер (участие коммутатора —
   ошибка).
2. Каждое имя в `AExports`/`BExports` резолвится в известную сеть или
   подсеть.
3. Оба списка присутствуют (пустой список легален = «ничего не отдаю»,
   но само поле обязательно — фильтр без списков считается ошибкой формата).

Следствие для сериализации: `a-exports`/`b-exports` пишутся **всегда**
(без `omitempty` в yaml/json-тегах внутри `LinkFilterDoc`), иначе пустой
список после roundtrip исчезнет и нарушит это правило. Опционален только
сам блок `filter`.

Ошибки в существующем стиле: `link[0]: ...`.

## Граф и поиск путей

`internal/graph/graph.go`:

```go
type Edge struct {
    To    Node
    Allow *edgeAllow // nil = неограниченное ребро
}

type edgeAllow struct {
    From, To map[string]struct{} // множества имён подсетей
}
```

При `Build`: для фильтрованной связи роутер–роутер экспорты обеих сторон
резолвятся в множества имён подсетей. Ребро `A→B` получает
`Allow{From: subs(AExports), To: subs(BExports)}`, ребро `B→A` — зеркально.

`internal/graph/pathfind.go`: `AllSimplePaths(src, dst)` во время DFS при
переходе по ребру с `Allow != nil` проверяет
`src.Name ∈ Allow.From && dst.Name ∈ Allow.To`; иначе ветка отсекается.
Обычные рёбра и доменные шины проверок не имеют.

Компилятор **не меняется**: `pairCache`/`RoutersOnPaths` просто получают
меньше путей для отфильтрованных пар.

## Поведение отрезанных пар

Если после учёта фильтров у пары src/dst какого-либо правила не осталось
ни одного пути — правило никуда не ставится (пустой набор целей), трафик
блокируется default policy. Это осознанное поведение, не ошибка:
compile/validate молча пропускают такие пары.

## HTTP API

`internal/httpapi/dto.go`:

```go
type LinkFilterDoc struct {
    AExports []string `json:"aExports" yaml:"a-exports"`
    BExports []string `json:"bExports" yaml:"b-exports"`
}
// Внимание: без omitempty внутри LinkFilterDoc — пустые списки
// сериализуются всегда (см. «Валидация», п. 3).

type LinkDoc struct {
    A      EndpointDoc    `json:"a" yaml:"a"`
    B      EndpointDoc    `json:"b" yaml:"b"`
    Filter *LinkFilterDoc `json:"filter,omitempty" yaml:"filter,omitempty"`
}
```

Эндпоинты не меняются: топология сохраняется целиком через
`PUT /api/topology`, который уже прогоняет `Validate`. Конвертация
обычная↔фильтрованная — установить/обнулить поле `filter`.

## UI

### Страница «Связи» `/ui/links`

Новые `links.html` + `links.js` + `links_page.test.js`, пункт в общей
навигации:

- Таблица всех связей: пара устройств, бейдж режима (`обычная` /
  `фильтрованная`).
- Кнопка «Сделать фильтрованной» у обычной связи (создаёт `filter` с
  пустыми списками) и «Вернуть обычную» у фильтрованной (удаляет поле).
- Редактор двух списков экспорта (сторона A / сторона B): мультивыбор из
  сетей и подсетей, сгруппированный по секциям.
- Сохранение — `PUT /api/topology` с сохранением остальных разделов
  verbatim; ошибки валидации — существующим error-паттерном страниц;
  dirty guard подключается как на других страницах.

### Канвас топологии

- Фильтрованная связь рисуется пунктиром акцентным цветом, отличимым от
  обычной линии (класс в `style.css`, класс проставляется в
  `topology.js` при рендере провода).
- Подсказка при наведении перечисляет экспорты: `MARKET → MAIN`.

Инструмент «connect» создаёт только обычные связи; конвертация — со
страницы «Связи». После правок web-ассетов обязательна пересборка
бинарника (go:embed).

## Тестирование

| Слой     | Что покрываем |
|----------|---------------|
| topology | загрузка YAML с/без filter; все три правила валидации |
| graph    | путь разрешён при подходящих экспортах; отсечён при неподходящих; нет «просачивания» обходом; обычные связи без изменений |
| httpapi  | roundtrip filter через GET/PUT /api/topology; ошибки валидации |
| web (node --test) | links_page: конвертация туда/обратно, правка экспортов, сохранение verbatim; topology_render: пунктирный класс у фильтрованной связи |

Проверка после изменений: `go build ./...`, `go vet ./...`,
`gofmt -l .`, `go test ./...`,
`node --test 'internal/httpapi/web/*.test.js'`.
