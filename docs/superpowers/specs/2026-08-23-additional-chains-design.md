# Дизайн: дополнительные цепочки (jump между цепочками)

Дата: 2026-08-23
Статус: согласован с пользователем (подход A: явные цепочки; `-j` с возвратом; единый placement; `jump_to` отдельным полем)

## Цель

Дать возможность объявлять в политике несколько iptables-цепочек и направлять
трафик из одной цепочки в другую действием `jump`. Сценарий: «супер-опасным»
пользователям — ограниченный доступ (отдельная цепочка со своим дефолтом
`deny`), остальным — обычная политика.

## Принятые решения (из брейншторма)

1. **Явные цепочки в YAML** (вариант A): список цепочек, у каждой — имя,
   дефолтное действие и свои правила. Никакой магии неявных цепочек.
2. **Семантика `-j`, не `-g`** (вариант A): если доп. цепочка заканчивается
   дефолтом `return` (или правилом `return`), трафик возвращается в вызвавшую
   цепочку и продолжает идти по следующим правилам. Дефолт `allow`/`deny` —
   терминальный вердикт.
3. **Единый placement** (вариант A): правила всех цепочек проходят тот же
   конвейер (резолв зон → pathfinding → placement на транзитных роутерах).
   Компилятор гарантирует: если на устройство попал прыжок в цепочку X,
   цепочка X существует на этом устройстве (хотя бы пустая, с дефолтом) —
   иначе скрипт не применится.
4. **Синтаксис** (вариант A): `action: jump` + отдельное поле `jump_to`.
   `Action` остаётся чистым enum'ом.

## Секция 1. Модель (`internal/rules`)

```go
type Action string // + ActionJump Action = "jump"

type Chain struct {
    Name          string        // имя iptables-цепочки
    DefaultAction Action        // allow | deny | return
    ChainPosition ChainPosition // значим только для главной цепочки
    Rules         []Rule
}

type Rule struct {
    // ...как сейчас...
    JumpTo string // цель прыжка для action == jump
}

type Policy struct {
    Chains []Chain // первая цепочка — главная (её jump ставится в FORWARD)
}
```

### Валидация (`rules.Validate`)

- `jump` без `jump_to`, с `jump_to` на несуществующую цепочку или в самого
  себя — ошибка.
- Циклы прыжков (A→B→A) — ошибка (обход графа прыжков).
- Имена цепочек уникальны и непусты; `jump_to` допустим только при
  `action == jump` (и наоборот: `jump_to` без `action: jump` — ошибка).
- `ChainPosition` у не-первых цепочек игнорируется (или запрещён — запрет
  явнее, выбираем запрет).

### Обратная совместимость загрузки

Текущий формат (top-level `defaultAction/chainName/chainPosition/rules`)
читается как политика с одной главной цепочкой. Новый формат — top-level
`chains:`. Сохранение всегда пишет новый формат.

## Секция 2. Компилятор (`internal/compiler`)

- Правила всех цепочек проходят существующий конвейер без изменений:
  `expandAtomic` → pathfinding → placement → дедуп.
- `CompiledRule` получает поле `Chain string` (цепочка-владелец) и
  `JumpTo string`; дедуп-ключ расширяется парой `(chain, jumpTo)`.
- `DeviceRuleset.Rules` сортируется по цепочке-владельцу, внутри цепочки —
  по-прежнему порядок политики.
- **Гарантия целостности**: перед рендером компилятор добавляет на каждое
  устройство недостающие целевые цепочки прыжков как пустые (только
  conntrack-правило и дефолт). Прыжок в несуществующую цепочку сломал бы
  применение скрипта на устройстве.
- `DeviceRuleset` получает `Chains []CompiledChain` вместо плоского
  `ChainName`:

```go
type CompiledChain struct {
    Name      string
    Primary   bool          // главная: её jump ставится в FORWARD
    Default   rules.Action
    Rules     []CompiledRule
}
```

## Секция 3. Рендер (`internal/render`)

Скрипт одного устройства:

1. Создать все цепочки (`iptables -N ... || true`).
2. Удалить и заново вставить jump в FORWARD только для primary-цепочки
   (семантика позиционирования `top/bottom` — как сейчас).
3. Для каждой цепочки: flush, conntrack-правило, правила по порядку,
   дефолт последним.
4. `jump` рендерится как `-j <JumpTo>`, `return` — `RETURN` (уже так).

Порядок создания цепочек не важен; flush чужих цепочек не производится —
по-прежнему трогаем только собственные.

## Секция 4. Симулятор (`internal/simulate`)

Проход по правилам устройства умеет заходить в доп. цепочки:

- `jump X` → спуск в X; вердикт X `return` (правилом или дефолтом) →
  продолжение со следующего правила вызывающей цепочки.
- Вердикты и причины упоминают цепочку явно («прыжок в цепочку X»,
  «цепочка X возвращает трафик»), как это уже делается для `return`
  относительно FORWARD.
- Цикл прыжков невозможен по построению (валимся на этапе загрузки),
  глубина ограничена числом цепочек.

UI симуляции структурно не меняется.

## Секция 5. HTTP API и UI

### DTO (`internal/httpapi/dto.go`)

Документ правил становится списком цепочек (поле `chains`); старый плоский
вид читается, пишется новый. `PUT /api/rules` валидируется сервером
авторитативно, как сейчас.

### Страница «Правила» (`web/rules.html`, `web/rules.js`)

- Над таблицей — переключатель цепочек (табы): главная + доп., кнопка
  «+ цепочка». Таблица показывает правила выбранной цепочки;
  перемещение/удаление/создание — в её пределах.
- Панель настроек: для главной — default/имя/позиция в FORWARD (как сейчас);
  для доп. — имя + default.
- Модалка правила: при `action = jump` появляется комбобокс «Перейти в
  цепочку» (все цепочки кроме текущей). `draftHint` дополняется проверками:
  jump без цели; имя цепочки пустое/дубликат.
- Удаление цепочки запрещено, если на неё ссылается `jump_to` другой цепочки
  (проверка на клиенте + сервером при сохранении).

### Фильтрация таблицы

Колонка Action фильтрует и по `jump`; колонка с целью прыжка попадает в
общий поиск по имени/комментарию не требуется — цель видна в строке правила.

## Секция 6. Тесты

- `rules`: загрузка нового и старого формата, все случаи валидации
  (несуществующая цель, цикл, `jump_to` без `jump`, дубль имён, позиция у
  не-главной).
- `compiler`: прыжок размещается на транзитных роутерах пути; целевая цепочка
  досоздаётся пустой на устройствах с прыжком; дедуп не склеивает правила
  разных цепочек.
- `render`: мультицепочный скрипт (idempotent, primary-jump один, дефолты на
  месте, `-j` для прыжков).
- `simulate`: терминальная доп. цепочка, возврат из доп. цепочки, текст
  причин.
- Web JS (`node --test`): табы цепочек, показ поля jump_to, draftHint,
  блокировка удаления связанной цепочки.
