# Дизайн: линтер правил

Дата: 2026-08-26
Статус: принят к реализации

## Контекст и цели

`Policy.Validate` (`internal/rules/validate.go`) сегодня проверяет только
структуру: существование ссылок, синтаксис портов, отсутствие циклов
`jump`. Логику самих правил — перекрытие, недостижимость, дублирование —
никто не проверяет. С ростом числа цепочек и правил это легко привести к
мёртвым правилам (никогда не сработают) или противоречиям, которые видны
только при ручном разборе.

Цель — статический анализатор политики (`internal/lint`), который находит
такие проблемы и показывает их пользователю на странице «Правила». Только
предупреждения/подсказки — линтер ничего не блокирует (компиляция и
сохранение правил работают независимо от его находок).

Не входит в эту фичу: анализ с учётом топологии/маршрутизации (это уже
делает `internal/diagnose` для конкретного потока) и CLI-команда — линтер
доступен только через веб-интерфейс.

## Сравнение правил по IP-диапазонам

Правила ссылаются на `src`/`dst` по именам (подсеть, сеть, набор,
литеральный CIDR, `any`), и разные имена могут описывать одно и то же
множество адресов. Чтобы находить реальные перекрытия, а не только
текстуальные совпадения имён, каждый эндпоинт резолвится в список
CIDR через уже существующие `Topology.EntityCIDRs` (подсеть/сеть/набор) и
`topology.ParseEndpointPrefix` (литерал); `any` — сентинел «покрывает
всё».

Резолвнутые списки CIDR сводятся к отрезкам `[start,end]` (128-битное
представление адреса) и сравниваются интервальной техникой — тем же
приёмом, которым `compiler/match.go: portOverlap` уже сравнивает диапазоны
портов. Две операции нужны на парах правил:

- **overlap** — пересекаются ли множества хотя бы частично;
- **covers** — покрывает ли объединение отрезков одного правила полностью
  отрезки другого (после слияния перекрывающихся отрезков в каждом
  множестве).

Совпадение правил по `src`×`dst`×`proto`×`ports` — конъюнкция overlap/covers
по каждому измерению отдельно (порты — уже готовый `portOverlap`-стиль,
IP — новый, `proto` — точное совпадение или `any`).

## Пакет `internal/lint`

По образцу `internal/diagnose`: чистые функции, не зависящие от
CLI/HTTP.

```go
package lint

type Severity string

const (
    SeverityWarning Severity = "warning"
    SeverityInfo    Severity = "info"
)

type Finding struct {
    Severity Severity
    Chain    string
    Rules    []string // одно или два имени правила, которых касается находка
    Message  string
}

func Check(pol *rules.Policy, topo *topology.Topology) []Finding
```

`Check` прогоняет пять независимых проверок (см. ниже) и возвращает их
находки в стабильном порядке (по цепочке, затем по порядку правил) —
детерминированность важна для тестов и для того, чтобы UI не дёргался.

### Проверки

1. **Недостижимое правило** — в пределах одной цепочки более раннее
   правило `covers` более позднее по всем измерениям. Два подслучая
   разного текста находки: совпадающий `action` («правило-дубликат,
   никогда не применяется») и разный (более раннее правило решает исход
   первым — позднее не имеет эффекта, даже если задумывалось иначе).
2. **Частичное пересечение с конфликтующим action** — `overlap`, но не
   `covers`, в любую сторону, и `action` двух правил различается —
   предупреждение, что для пересекающегося подмножества трафика исход
   зависит от порядка правил.
3. **Мёртвая цепочка** — цепочка, кроме первой (primary), на которую не
   ссылается ни один `jumpTo` во всей политике.
4. **Симметрия/`mirror`**:
   - `mirror: true`, но `src` и `dst` самого правила уже `overlap` —
     мёртвый флаг, зеркалирование не даёт новых пар.
   - два правила в одной цепочке — точные зеркала (у одного `src`/`dst`
     переставлены местами относительно другого, `proto`/`ports`/`action`
     совпадают, у обоих `mirror: false`) — подсказка объединить в одно
     правило с `mirror: true`.
5. **Слишком широкое правило** — `src == [any]`, `dst == [any]`,
   `proto == any`, `Comment == ""` — подсказка (info) сопроводить
   правило комментарием, объясняющим намерение.

Каждая проверка — отдельная функция `checkXxx(pol, topo) []Finding`,
независимая от остальных: добавление новой проверки в будущем не требует
трогать существующие.

## HTTP API

`internal/app`: `func Lint(ctx context.Context, log *slog.Logger, topo *topology.Topology, pol *rules.Policy) ([]lint.Finding, error)` —
тонкая обёртка, аналогичная `app.Diagnose`.

`internal/httpapi`: новый хендлер `GET /api/lint`, без тела запроса —
берёт текущие topology/subnets/rules из store (как остальные `GET`-эндпоинты
страницы правил), зовёт `app.Lint`, отдаёт JSON:

```json
{ "findings": [
  { "severity": "warning", "chain": "FIRENET-FWD",
    "rules": ["main-to-market"], "message": "..." }
] }
```

Проверка запускается только по явному запросу со страницы — без live-режима
по мере редактирования, без периодического опроса.

## UI

Страница `rules.html`/`rules.js`:

- Кнопка «Проверить» в `toolbar-actions` рядом с существующей кнопкой
  поиска (`.btn-search`).
- По клику — `GET /api/lint`, результат — панель со списком находок
  (severity как цветной бейдж warning/info, текст сообщения).
- Клик по находке переключает на нужную цепочку (`switchChain`, уже
  существует для jump-to) и подсвечивает затронутые строки таблицы
  правил новым CSS-классом (аналогично точечной подсветке при переходе к
  правилу-цели `jump`, если такая есть, иначе — новый минимальный класс
  `.lint-highlighted` в `style.css`, снимаемый при следующем клике/скролле
  пользователя вручную или по таймеру ~2с — конкретный механизм снятия
  подсветки оставлен на реализацию, раз он не влияет на данные и API).
- Панель закрывается независимо от панели поиска; обе могут быть открыты
  по очереди, не одновременно (как сейчас устроено для других toolbar-панелей).

После правок веб-ассетов обязательна пересборка бинарника (`go:embed`).

## Тестирование

| Слой | Что покрываем |
|------|----------------|
| `internal/lint` | табличные тесты на каждую из пяти проверок: срабатывает / не срабатывает на пограничных случаях (частичное перекрытие, разные имена с одинаковым CIDR, `any`, зеркальные правила, мёртвая цепочка при наличии/отсутствии `jumpTo`) |
| `internal/lint` | интервальный overlap/covers для IP: смежные, вложенные, частично перекрывающиеся CIDR из разных сущностей (subnet vs set с тем же диапазоном) |
| `internal/app` | `Lint` возвращает находки из `lint.Check`, ошибки загрузки топологии/правил всплывают |
| `internal/httpapi` | `GET /api/lint` отдаёт JSON нужной формы, пустой список при отсутствии находок |
| web (`node --test`) | рендер панели находок, клик по находке переключает цепочку |

Проверка после изменений: `go build ./...`, `go vet ./...`, `gofmt -l .`,
`go test ./...`, `node --test 'internal/httpapi/web/*.test.js'`.
