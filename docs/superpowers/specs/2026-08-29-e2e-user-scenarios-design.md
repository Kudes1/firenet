# Дизайн: пользовательские E2E-сценарные тесты

Дата: 2026-08-29
Статус: утверждён (обсуждение в чате, ответы пользователя зафиксированы)

## Проблема

Проект развивается через TDD: unit-тесты бэкенда (Go) и unit-тесты фронтенда
(node:test с рукописными DOM-заглушками) хорошо ловят регрессии внутри своих
слоёв, но между слоями есть щель:

- UI-тесты исполняют JS не в настоящем DOM, а в заглушках — реальные события
  канваса, поведение Alpine/htmx и вёрстку они не проверяют;
- Go-тесты проверяют API без настоящего UI — контракт «что UI шлёт / что ждёт
  в ответ» никто не держит целиком.

Баги, найденные при ручном тестировании приложения, попадают именно в эту
щель, и каждый такой баг приходится разбирать вручную. Нужен слой тестов,
который исполняет действия так, как их делает пользователь: реальный браузер,
реальный сервер, реальные клики.

## Решение

Playwright E2E-тесты против полного стека: реальный Chromium + бинарник
`firenet serve` + реальный PostgreSQL в одноразовом docker-контейнере.

Один сценарий = пользовательская история: «открыл страницу → сделал действия
инструментами/панелями → увидел результат». Проверка идёт по всем трём слоям
сразу (UI, API, контракт).

Зафиксированные решения (выбор пользователя):

- инструмент — Playwright (реальный браузер);
- база — docker-контейнер per-run (одноразовый Postgres, полная изоляция);
- тесты не зависят от окружения разработчика.

### Расположение и запуск

- `e2e/` в корне репозитория, свой `package.json` с единственной
  dev-зависимостью `@playwright/test`. Правило AGENTS.md «только встроенные
  модули node» сохраняется для приложения: node_modules появляются только в
  `e2e/` и не участвуют в сборке/работе приложения.
- `make test-e2e`: сборка бинарника (`make build`) → запуск playwright.
  Существующие цели (`go test`, `node --test web/*.test.js`) не меняются.
- CI/среда запуска требует docker и chromium (playwright ставит браузер сам
  через `npx playwright install chromium`).

### Инфраструктура прогона

`playwright.config.js` с `globalSetup` / `globalTeardown`:

1. **globalSetup**
   - поднимает одноразовый контейнер Postgres 16 (`docker run`, случайное
     имя, случайный порт, tmpfs-том — контейнер удаляется после прогона);
   - запускает `bin/firenet serve --addr 127.0.0.1:<порт>` с env:
     `FIRENET_DATABASE_URL` на ephemeral БД, `FIRENET_ADMIN_USER=e2e-admin`,
     `FIRENET_ADMIN_PASSWORD` (админ бутстрапится сервером сам, см.
     `internal/cli/serve.go`);
   - ждёт готовности (poll `GET /api/me` до ответа не-ошибки);
   - пишет адрес сервера и креды в файл-артефакт для воркеров.
2. **globalTeardown**: SIGTERM серверу, `docker rm -f` контейнера.

Каждый прогон получает чистую БД — тесты самодостаточны и независимы.

### Паттерн сценариев: arrange via API → act via UI → assert

- **Arrange** — подготовка данных через API-клиент Playwright
  (`helpers/api.js`: логин `POST /api/login`, операции над draft напрямую).
  Быстро и надёжно; никаких кликов «ради подготовки данных».
- **Act** — всё, что тестируем, исполняется как пользователь: реальные клики
  по канвасу и панелям (инструменты создания, переименование через панель,
  инструмент «связь», переключение типа связи).
- **Assert** — через UI (объект виден / переименован / исчез) плюс при
  необходимости контрольное чтение состояния через API.

### Селекторы

Ключевые интерактивные элементы помечаются `data-testid` — минимальные правки
в `web/*.html` / `web/*.js`. Селекторы собираются только в `helpers/ui.js`.

## Сценарии первой итерации

По одному `*.spec.js` на группу, общие помощники — в `e2e/helpers/`.

| # | Сценарий | arrange | act |
|---|----------|---------|-----|
| 1 | Создание объектов: роутер, свитч, сеть, связь | пустой draft | инструменты создания |
| 2 | Переименование одиночного объекта | объект через API | панель свойств |
| 3 | Переименование связанного объекта (ссылки в связях обновились) | объект + связь через API | панель свойств |
| 4 | Переименование вложенного объекта: подсеть внутри сети; набор, на который ссылается правило | объекты через API | панель свойств |
| 5 | Удаление одиночного объекта | объект через API | UI-удаление |
| 6 | Удаление связанного объекта (связи исчезают) | объект + связь через API | UI-удаление |
| 7 | Удаление вложенного объекта | через API | UI-удаление |
| 8 | Инструмент «связь»: соединение двух устройств | два устройства через API | инструмент связи |
| 9 | Переключение связи Обычная ↔ Фильтрованная | устройства + связь через API | панель связи |

Сценарии 2–7 запускаются для всех родов объектов, где применимо (устройство,
сеть, подсеть, набор, связь) — параметризованно, а не девятью копиями кода.

## Структура файлов

```
e2e/
  package.json            # dev-зависимость: @playwright/test
  playwright.config.js
  global-setup.js         # docker + serve + ожидание готовности
  global-teardown.js
  helpers/
    api.js                # API-клиент: логин, draft-операции
    ui.js                 # селекторы (data-testid), клики, ожидания
  scenarios/
    create-objects.spec.js
    rename.spec.js        # сценарии 2–4, параметризованы по роду объекта
    delete.spec.js        # сценарии 5–7
    link-tool.spec.js     # сценарий 8
    link-filter.spec.js   # сценарий 9
```

В `.gitignore` добавляется `e2e/node_modules/` — исходники тестов в `e2e/`
коммитятся как обычный код.

## Компромиссы (осознанно принятые)

- Запуск тестов требует docker и занимает ~минуту из-за старта контейнера.
- Правки в продакшн-шаблонах: добавление `data-testid`.
- Playwright — единственное место в проекте с node_modules; в `go.mod` и в
  логике приложения он не попадает.

## Вне рамок

- Мультибраузерность (только chromium), параллельный прогон по воркерам,
  визуальные снепшот-тесты, нагрузочные сценарии — при необходимости позже.
- Переписывание существующих node:test / Go-тестов — они остаются как есть.
