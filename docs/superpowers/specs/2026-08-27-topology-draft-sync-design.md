# Дизайн: синхронизация редактора топологии с черновиком

Дата: 2026-08-27
Статус: утверждён

## Проблема

Редактор топологии изменяет локальный `State.topology` до нажатия общей
кнопки «Сохранить», но часть API уже читает сохранённый черновик. Поэтому
связь может быть видна на холсте и отсутствовать для расчёта кандидатов
фильтра; после сохранения локальный порядок связей также может отличаться
от канонического порядка хранилища. Индекс массива не является устойчивой
идентичностью связи.

## Цель и границы

Черновик на сервере становится единственным источником истины для редактора
топологии. В этой работе меняется только `/ui/topology`: устройства, сети,
связи, подключения сетей, объединения, фильтры и layout. Страницы подсетей,
правил и наборов сохраняют текущий пакетный механизм `PUT`.

Undo не реализуется. Все правки будут отдельными операциями, поэтому позже
клиент сможет хранить обратные операции и отправлять их тем же контрактом.

## Контракт API

Добавляется маршрут:

```
POST /api/drafts/{id}/topology/operations
```

Тело содержит одну типизированную операцию и обрабатывается с текущей
ревизией `X-Draft-Revision`. Операции покрывают:

- создание и удаление устройства, сети, связи или объединения;
- подключение/отключение сети от устройства;
- назначение/исключение устройства или сети из объединения;
- установку или удаление фильтра связи;
- изменение позиции устройства, сети, waypoints связи и камеры.

Связь в операциях и запросах кандидатов определяется канонической парой её
концов (`linkKey(a, b)`), а не позицией в массиве. API кандидатов принимает
устройства связи и сторону; сервер находит связь по паре и не принимает
индекс как идентификатор.

Сервер читает черновик, применяет операцию к полному `ProjectDoc`, проверяет
проект существующей валидацией и сохраняет через CAS. После успешной записи
он читает черновик заново и возвращает его канонический снимок для редактора:

```json
{
  "topology": { "devices": [], "links": [], "networks": [], "sets": [], "unions": [] },
  "layout": { "devices": {}, "networks": {}, "links": {}, "camera": {} }
}
```

Ответ содержит актуальную `X-Draft-Revision`. При конфликте ревизии сервер
возвращает 409; недопустимая операция возвращает 422 и не меняет черновик.
Существующие пакетные `GET`/`PUT` topology и layout остаются для совместимости,
но холст ими больше не пишет.

## Клиентский поток

Клиент хранит подтверждённый серверный снимок и очередь локальных операций.
Визуальная модель строится применением очереди к подтверждённому снимку, что
даёт мгновенный отклик без подмены источника истины. Одновременно в сеть уходит
ровно одна операция. После успеха клиент заменяет подтверждённый снимок
ответом сервера, удаляет завершённую операцию и заново накладывает оставшиеся.

Операции перемещения, накопившиеся до отправки, сворачиваются до последней
позиции для одного объекта. Действия, требующие сохранённую топологию
(например, настройка фильтра только что созданной связи), становятся доступны
после подтверждения операции создания. Индикатор страницы показывает
«Сохраняется», «Сохранено» или «Ошибка синхронизации»; предупреждение
`DirtyGuard` для страницы топологии отключается.

При 409 очередь останавливается, клиент заново читает topology и layout,
сбрасывает неподтверждённые операции и сообщает пользователю, что черновик
изменился в другой вкладке. Автоматически повторять операции нельзя: новая
топология могла сделать исходное действие неверным. При других ошибках
клиент также возвращается к последнему серверному снимку и оставляет действие
для ручного повторения.

## Серверные компоненты

`internal/httpapi` добавляет DTO операции, обработчик и маршрутизацию.
Обработчик использует текущие `ReadDraft`, `WriteDraft`, `loadTopologyDoc` и
проверки зависимостей; бизнес-логика хранения остаётся в `internal/pgstore`.
Общая операция topology/layout нужна потому, что ревизия черновика едина для
всех сущностей: отдельная несинхронизированная автозапись layout не должна
соревноваться с изменением связи.

Сортировка сущностей в `pgstore.fromEntities` остаётся канонической. Ответ
операции всегда содержит эту сортировку, поэтому ссылка и порядок на холсте
соответствуют сохранённому черновику сразу, без перезагрузки.

## Ошибки и сохранность

Операция применяется к копии документа и валидируется до `WriteDraft`;
частично изменённого черновика не бывает. Сетевые ошибки не считаются успехом:
локальная проекция откатывается к подтверждённому снимку после синхронизации.
Удаление остаётся действием без undo в первой версии, но каждое изменение
представлено отдельной командой, что создаёт точку расширения для истории и
обратных команд.

## Проверка

- Go HTTP-тесты: каждая операция изменяет черновик и возвращает канонический
  снимок; некорректная операция не сохраняется; конфликт ревизии возвращает
  409; связи, сохранённые в ином порядке, корректно находят кандидатов по
  паре устройств.
- Node-тесты холста: очередь сохраняет порядок, ответ сервера заменяет
  снимок, перемещения сворачиваются, 409 восстанавливает состояние, настройка
  фильтра ждёт создания связи.
- Полный набор проекта: `go build ./...`, `go vet ./...`, `gofmt -l .`,
  `go test ./...` и `node --test 'internal/httpapi/web/*.test.js'`.
